# Self-hosting — architecture for review

Status: **awaiting approval**. Nothing in "To build" has been written yet.
Decisions confirmed by the operator on 2026-07-26 are marked ✅.

---

## 1. The shape

Self-hosting is **the same product on the user's own accounts**. No alternate
stack, no second code path, nothing swapped for a "self-host edition".

```
   their phone / browser
            │
            ▼
   THEIR Cloudflare Worker  ──►  THEIR D1        (file index, same schema)
            │
            ├──────────────►  THEIR Firebase     (login only)
            │
            ├──────────────►  THEIR Telegram bot ──► THEIR private channel
            │                                        (encrypted 19MB chunks)
            │
            └──────────────►  THEIR serverless function (HEIC → JPEG, optional)
```

Everything is serverless and scales to zero. Nothing runs when nobody is using
it, which is what keeps it free.

**Not in the picture:** us. No shared worker, no shared database, no telemetry,
no callback. If we vanish, their install keeps working.

## 2. What the user provides

| | Where from | Free? |
|---|---|---|
| Telegram bot token | @BotFather, 2 messages | yes |
| Telegram channel id | new private channel + @userinfobot | yes |
| Cloudflare API token | dash → custom token, 3 permissions | yes |
| Firebase project id + Web API key | console → new project → enable Email/Password | yes |
| Vercel account (optional) | only for HEIC thumbnails | yes |

## 4. Setup flow

`node selfhost/bin/daemonclient.mjs setup` — seven steps, each validated
against the real service, each saved on completion so Ctrl-C resumes.

1. **Preflight** — Node ≥18, repo intact, internet reachable.
2. **Telegram** — token verified with `getMe`; channel verified by *actually
   posting a message and deleting it* (a bot can be in a channel and still be
   unable to write).
3. **Cloudflare** — token verified, account chosen, D1 created, schema applied.
4. **Firebase** — project id + Web API key, then a real `signInWithPassword`
   round-trip so a typo or a disabled provider fails here, not on their phone.
5. **Deploy** — build the worker from their checkout, upload with bindings,
   generate `SESSION_SECRET`, seed the Telegram config into their D1, wait for
   `/api/health`.
6. **Processor** (optional) — deploy instructions, paste URL, health check.
7. **Summary** — API address, sign-in, storage, next commands.

## 5. Dashboard — the honest complication

You chose reusing `accounts-portal`. It is the right UX call, but the portal
today is wired to the managed service in three ways that must be handled:

| Problem | Plan |
|---|---|
| Firebase config is hardcoded to our project | Read from `import.meta.env` with our values as defaults, so a self-hoster sets `VITE_FIREBASE_*` and builds |
| Onboarding flow assumes our Render setup service + Cloudflare OAuth provisioning | Detect self-host mode and skip the whole funnel: the CLI already provisioned everything, so it opens straight on the dashboard |
| Requires npm install + vite build | CLI runs the build and deploys to their Cloudflare Pages; documented manual path for Vercel/Netlify |

Net: roughly one new env-driven config module, one guard around the setup
funnel, and a CLI step. The managed portal keeps working unchanged.

**Already built and now redundant:** the standalone single-file dashboard
(`selfhost/dashboard/index.html`). I will delete it unless you want it kept as
the no-build fallback.

## 6. Updates

The worker asks GitHub once a day for the latest release tag, caches it in its
own D1 for 12 hours, and reports it. The dashboard shows a banner; nothing
happens automatically.

```
git pull && daemonclient update
```

re-applies schema changes, rebuilds from their checkout, redeploys, and reuses
the existing secrets — a rotated session secret would sign them out, a rotated
storage key would make their files unreadable.

The check is an anonymous GET to a public endpoint. It sends nothing about the
install and can be disabled by clearing `UPDATE_REPO`.

## 7. Security model

- Files encrypted AES-256-GCM before Telegram. Drive encrypts in the browser
  (the worker never sees plaintext); Photos encrypts on their own worker, which
  is what makes thumbnails, EXIF and dedup possible.
- Sessions signed with a per-install secret; the worker refuses to issue one if
  the secret is missing rather than falling back to something guessable.
- The processor verifies a real Firebase ID token (RS256 only, issuer +
  audience + expiry checked) and is pinned to a single uid.
- Setup state is 0600 and gitignored; `daemonclient doctor` prints a report with
  every secret redacted, because pasting a config dump into a public issue is
  how self-hosters get compromised.
- No signup endpoint, no bootstrap route, no admin backdoor.
