## 2. THE core finding — the storage primitive exists four times

The one thing this whole product is built on — *split a file into 19 MB chunks,
AES-GCM encrypt each, `sendDocument` to Telegram, record a manifest* — is
implemented independently in **four** places:

| # | File | Lines |
|---|---|---|
| 1 | `immich/web/src/lib/utils/daemonclient-drive.ts` | 393 |
| 2 | `drive/src/App.jsx` (+ `drive/src/crypto.js`) | — |
| 3 | `immich-api-shim/src/assets.ts` | 3,627 |
| 4 | `immich-api-shim/src/webdav.ts` | 527 |

`CHUNK_SIZE = 19 * 1024 * 1024` is hardcoded in at least **five** files — and
**twice inside `drive/src/App.jsx` alone** (lines 28 and 209).

**This is what makes "fix once, both get it" impossible today.** A bug in
chunking, encryption, or the manifest format must be found and fixed in four
places, by hand, correctly, every time. It is also why Photos and Drive drift
apart, and it is the single biggest obstacle to the operator's one-path vision.

**It is the reason to do the extraction before anything else is built on top.**

## 3. Web status — one gap, and it is small

| Path | Route | Status |
|---|---|---|
| Upload | Browser → Telegram directly; worker gets metadata only | ✅ client-direct |
| Read `original` | SW → Telegram via `dc-manifest` | ✅ client-direct |
| Read `thumbnail` | SW → Telegram via `dc-manifest` | ✅ client-direct |
| **Read `video/playback`** | **Through the worker** | ❌ **the gap** |

The service worker's direct-route test is:

```js
const ASSET_BINARY_REGEX = /^\/api\/assets\/[a-f0-9-]+\/(original|thumbnail)/;
```

`video/playback` is not matched, so every video stream is proxied by the
worker. On the free plan (10 ms CPU, 128 MB, 50 subrequests) a multi-chunk
video cannot fit — the worker is killed with **error 1102**, Cloudflare returns
an error page carrying no CORS headers, and the browser reports it as a CORS
failure. That is the entire content of the operator's console log.

**Fixing this one regex makes the web depend on the worker for JSON only.**

## 6. Self-host readiness

`selfhost/` already ships a dependency-free CLI (`setup`, `status`, `update`,
`web`, `dashboard`, `processor`, `doctor`) with passing tests. The gaps are:

1. **Bot creation still assumes our backend.** `backend-server/main.py` uses
   operator userbot sessions. The CLI must walk the user through BotFather.
2. **No curl bootstrap.** There is no `install.sh`.
3. **No path-based hosting.** Self-host should serve one site:
   `user.web.app` (dashboard), `/photos`, `/drive`.
4. **Build-time defaults leak.** Some apps still fall back to operator hosts
   when the self-host env var is unset.

---

## 7. What this means for sequencing

The audit changes the order. **The one-path extraction must come before the
self-host script**, because the script's whole promise is "we fix it once and
both of you get it" — and today a fix must be applied four times. Building the
self-host installer on top of four divergent copies would bake the divergence
in permanently.

Correct order:

1. **Close the web gap** (`video/playback`) — small, high value, provable today.
2. **Extract the storage core to one module** — the actual "one path".
3. **Clean the repo** — delete dead code, move operator-only material out.
4. **Remove operator identifiers** — make a fork genuinely forkable.
5. **Build the self-host installer** on top of the now-single path.
6. **CI + gates** enforce that the path stays single.
7. **Only then** consider apps.
