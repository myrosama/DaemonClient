# New Drive — Phase 2: worker release W1 (plan)

Spec: `docs/drive/FILEBROWSER_SPEC.md` (draft PR #5) §4 *Trash*, *Thumbnails*,
*Integrity* and §6 *Worker release W1*. Code: branch `feat/drive-w1`, from
`main`. Written before the code; nothing is built or deployed until the owner
approves this plan.

W1 is one per-user worker release (`immich-api-shim`, shipped as the bundle
embedded in `deployment-service`). It adds Trash, thumbnails and part
confirmation on the worker side, and changes no stored data. The classic Drive
app, WebDAV mounts and the mobile apps keep working against it.

## Decisions for the owner

| # | Question | Proposal |
|---|---|---|
| D1 | Can *Delete forever* (the purge mark) apply to an item that isn't in Trash? | **No.** The mark is accepted only for an item that is trashed or inside a trashed folder. Nothing leaves Telegram without passing through Trash first. |
| D2 | Restoring an item whose folder is gone, trashed or being deleted | It goes to the top level (otherwise it would stay hidden). |
| D3 | Who expires items after 30 days | The worker flags them (`expired: true`) in the Trash listing, by its own clock; the app then purges them. No GET changes data. |
| D4 | WebDAV MOVE onto an existing file (how Finder and GNOME save) | The file it replaces goes to Trash. Today both rows stay, as two files with one name. |
| D5 | WebDAV temp files (`._*`, `.goutputstream-*`, `~$*`, `.~lock.*`) deleted by the file manager | **Deleted outright** (row and parts), not sent to Trash; otherwise every save fills the Trash. All other WebDAV deletes go to Trash. |
| D6 | Canary | The test account's worker only (as for release D), then the fleet. |

## Contract

**Columns** (`files`, additive, all nullable `TEXT`): `trashedAt` (ISO time,
worker clock), `purgingAt` (ISO time; set = marked for deletion), `thumb`
(JSON `{"message_id": n, "file_id": "..."}`, ≤ 512 bytes). Added to
`schema/schema.mjs` (`MIGRATION_SQL`, `DRIVE_MIGRATION_SQL`) for new
databases, and by the worker itself for existing ones (below).

**Visibility.** An item is *hidden* if it is trashed, marked, or has a trashed
or marked ancestor. One function decides this for the whole tree, once per
request, with a visited set and a depth limit (existing data has no move
check, so it may hold cycles); an orphan (parent missing) stays visible, as
today.

**Routes** (`/api/drive/...`, owner-checked like today):

| Route | W1 behaviour |
|---|---|
| `GET /config` | Adds `driveApi: 1`. Absent = an older worker; the new app then shows "your Drive is being updated" and makes no writes. |
| `GET /files[?parentId=]` | Leaves out hidden items (with or without `parentId`). |
| `GET /files?trashed=1` | Hidden items only: trashed items, the contents of trashed folders and marked items, each with `trashedAt`, `purgingAt` and `expired` (top-level trashed items older than 30 days by the worker's clock). |
| `POST /files` (create or full save) | Accepts `thumb`. Never sets `trashedAt` or `purgingAt`; a save leaves both as they are. Leaving `thumb` out keeps it unless `messages` changed (compared parsed), which clears it. Refuses (409) a save over a marked row. If `parentId` changes on an existing id: the move check. |
| `PATCH /files/:id` | Refuses moving a folder into itself or a descendant, or into a parent that doesn't exist or is hidden (409). Refuses a marked item (409). |
| `POST /files/:id/trash` | Sets `trashedAt` (if not set) and `updatedAt`. Refuses a marked item. Idempotent. |
| `POST /files/:id/restore` | Refuses a marked item (409). Clears `trashedAt`; moves to the top level if the parent is gone, trashed or marked (D2). Restoring a folder brings back its contents. |
| `POST /files/:id/purge` | D1: refuses an item that isn't trashed or inside a trashed folder (409). Marks the item and everything inside it (`purgingAt`), one recursive statement filtered by `ownerId`, cycle-safe. Returns the marked items (with `messages` and `thumb`) so the app can delete their Telegram messages. |
| `DELETE /files/:id` | Unmarked items: as today (the classic app deletes that way). A marked folder that still has children: refused (409). |
| `GET /usage` | Unchanged: counts Trash until it is emptied. |

**WebDAV** (`/dav/`):
- Every path lookup uses visible items only: PROPFIND, GET/HEAD, PUT (parent
  and existing target), MKCOL's exists check, MOVE source and destination.
- DELETE moves the item to Trash (its contents follow by ancestry), except
  temp files (D5). No Telegram messages are deleted.
- MOVE: the move check; an existing destination file goes to Trash (D4).
- PUT, part confirmation: after each `sendDocument`, Telegram's `file_size`
  must equal the bytes sent (the ciphertext when encrypted). A mismatch or a
  missing size deletes that message and resends, at most 3 times per part,
  waiting as long as a 429 asks (30 s at most in total). The row is saved only
  when every part is confirmed; on failure every message sent is deleted and
  the client gets 502. Worst case per PUT: 5 parts × 4 sends + 15 deletes + 5
  old parts + 1 old thumbnail = 41 subrequests (limit 50); the 90 MB cap stays.
- PUT overwrite: as today the old parts are deleted after the new row is
  saved; the old thumbnail message is deleted too and `thumb` cleared.

**Schema on old workers.** Auto-update ships code only, so the worker adds the
columns itself, from **both** entry points (`handleDrive` and `handleWebDav`;
a mount is often the first caller after an update). Each `ALTER TABLE ... ADD
COLUMN` counts as done only if it succeeds or fails with "duplicate column";
any other error leaves the flag unset and the request returns 503, so an
isolate never queries a column that isn't there.

## Gate 1 — tests first (vitest, `immich-api-shim`)

- Visibility: trashed, marked, under a trashed or marked ancestor; a cycle
  (A→B→A) and a deep chain terminate; an orphan stays visible; `parentId`
  listing of a trashed folder's child folder returns nothing.
- Trash, restore (into the folder; to the top level when the parent is gone,
  trashed or marked), purge (D1 refusal; marks the subtree; owner filter;
  cycle-safe), DELETE (marked folder with children refused; unmarked delete as
  today, a folder's included).
- Expiry: `expired` from the worker's clock at 30 days ± 1 s.
- Saves: a save without `trashedAt`/`purgingAt` keeps them; `thumb` kept when
  `messages` is unchanged, cleared when it changed, a supplied `thumb` wins; a
  malformed `thumb` is rejected; a save over a marked row is refused; a save
  that changes `parentId` runs the move check.
- Moves: into itself, into a descendant, into a missing or hidden parent.
- WebDAV: lookups skip hidden items; DELETE → Trash; temp-file DELETE → gone;
  MOVE overwrite → the old file in Trash; PUT part confirmation (size
  mismatch → resend; three failures → 502 and every sent message deleted;
  429 honoured); PUT overwrite clears `thumb` and deletes the old thumbnail.
- Schema: the first request after an update is WebDAV; an `ALTER` failing for
  another reason leaves the flag unset (503), and the next request retries.
- `driveApi: 1` in `/config`.
- `schema-source.test.mjs` (self-host) still passes with the new columns.

## Gate 2 — the canary (after approval)

Deploy `deployment-service` with the new bundle and
`SHIM_CANARY_WORKERS` set to the test account's worker; update that worker; confirm its
`X-Worker-Version`. Then on that account: the classic app uploads, lists,
renames, moves and deletes (a folder too); the new routes by `curl` (trash,
listing hides, restore, purge mark, delete); a WebDAV mount (GNOME Files):
browse, upload 0 B / 19 MB + 1 / 60 MB, save over a file (D4), delete (Trash)
and a temp file (D5). Logs tailed with URL redaction.

## Rollout and rollback

- **Fleet:** redeploy `deployment-service` without the canary variable; the
  10-minute fleet update and sign-in auto-update carry W1 to every worker.
  The five workers that can't update today (three need their owner to
  reconnect Cloudflare, two failed to deploy) stay on the old code; the new
  app's `driveApi` check covers them.
- **Rollback:** redeploy the previous bundle. The columns stay (additive), but
  old code ignores them, so trashed and marked items reappear in every
  listing, and an item that was mid-purge can show with parts already gone.
  Roll back only before the new app ships writes (phase 4), or accept that.
- **Mobile:** the MacBook gets the contract change in NOW.md: hidden rows, the
  new routes, `driveApi`, and that DELETE still accepts unmarked items under
  W1.
